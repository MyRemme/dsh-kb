# 设计说明

> 一句话：把每次会话里"想明白的事"沉淀成不可变的事实卡，树和图只是它的两副视图。

被实现驱动，不是被理念驱动 —— 下面每条都对应 `lib/` 里的一段代码和一次实测。

---

## 一、问题定义

长期记忆有三类失败：

| 失败 | 表现 | 机制 |
|---|---|---|
| **遗忘** | 问"上次那个怎么弄的"，答不上 | 索引 + 检索 |
| **失真** | 记得，但记错了；摘要层层压缩偏离原意 | 卡不可变 + 回指原文 + 摘要可重算 |
| **腐烂** | 旧结论还在，被当成现行方案 | status + supersedes + 时间衰减 |

权重：**失真和腐烂 > 召回率**。召回差了你换个词再查一次就行；记错了你会照着错的干。

---

## 二、为什么不是纯树，也不是纯星

**纯树的三种死法**

1. 单父。每条知识必须恰好挂一个枝。实测一个会话经常横跨四个主题（解包 + 材质槽位 + Unity 版本 + 导出工具），挂哪都错。
2. 分类成本随规模线性上涨。写到第 500 条时，你花在"这该归哪"上的时间超过知识本身的价值，然后你不写了。
3. 表达不了取代。树没有"这条已被那条推翻"的位置。

**纯星（纯图 / 纯向量）的三种死法**

1. 召回全靠相似度，返回一堆语义像但没用的碎片。
2. 没有层级 = 无法做范围限定（"只看 dsh 相关的"）。
3. 没有锚点去重，无限膨胀，不知道哪些过期。

**结论**：树和星是可视化隐喻，不是数据结构。真问题是**谁做真相、谁做索引**。

## 三、一真三投影

```
                    ┌──────────────────────────────┐
                    │  fact  账本（唯一真相）       │
                    │  一行 = 一条不可变事实卡      │
                    └──────────┬───────────────────┘
                               │ 投影（全部可重建）
          ┌────────────────────┼────────────────────┐
          ▼                    ▼                    ▼
   ┌─────────────┐      ┌─────────────┐      ┌─────────────┐
   │ node 骨架树 │      │ edge 关系图 │      │ FTS 索引    │
   │ 物化路径    │      │ 1 跳扩展    │      │ bigram 词法 │
   │ 多归属      │      │ 演化链      │      │ + 覆盖率精排│
   │ 摘要=缓存   │      │             │      │             │
   └─────────────┘      └─────────────┘      └─────────────┘
```

| 需求 | 载体 | 约束 |
|---|---|---|
| 这条知识是什么 | `fact` 行 | 不可变；改了就是新卡 |
| 它归哪一类 | `paths` 数组 + `node` | 多归属；`path` 只是主展现 |
| 它和什么相关 | `edge` | 写入时建，不事后批处理 |
| 怎么被找到 | FTS5 + 覆盖率精排 | 词法是主力 |

`node.summary` 是缓存，不是真相。枝的边界随卡片漂移，所以摘要必须随时能重算（`lib/digest.js`，实测 12 个节点 0.1 秒）。把它当真相存 = 日后无法纠正。

## 四、写入路径

```
会话文件 (.jsonl.zstd, 多帧)
   │  逐帧解压 → 事件流
   ▼
自动抽取 (kb_ingest)               手工沉淀 (kb_add)
   ├─ episode 卡：一会话一卡       ├─ 决定、偏好、流程
   ├─ 分段卡：compaction 摘要拆段   ├─ "为什么不用 B"
   └─ intent 卡：用户原话节选       └─ 环境事实变化
   │                               │
   └──────────┬────────────────────┘
              ▼
      去重（内容哈希 OR 标题）
              ▼
      建边 contains / supersedes
              ▼
      ensure_node（多归属枝）
```

**分工只有一条**：自动层只能提取"已经写在会话里的事实"，**"为什么"必须当场由模型写下**。指望从事件流推理由，得到的是幻觉。

**去重双键**：内容哈希（同内容不同标题）+ 标题（同结论不同措辞）。前者防重复录入，后者让"同一结论的补充"合并而不是长出第二张卡。

**去噪**：`runtime-context`、`<system-reminder>`、skill catalog 每次都一样，不是知识。

---

## 五、读取路径：三级渐进

| 层 | 载体 | 回答什么 |
|---|---|---|
| L1 | `node.summary` | 这枝是什么（几十字） |
| L2 | `fact.body` | 具体结论（几百字） |
| L3 | `source_ref` → 原会话 | 原话、报错全文、命令 |

多数 RAG 只做 L2。L3 才是真能"找回去" —— `source_ref` 存 `session-id#seq`，能定位到具体事件。

## 六、检索

```
query
 ├─ 通道 A  词法  FTS5(bigram) AND → 不足退 OR     ← 精确词，主力
 ├─ 通道 B  兜底  子串 LIKE                         ← 短查询/拼写异常
 └─ 通道 C  图    对 top3 走 1 跳 contains          ← 补上下文
        ↓
   精排（纯计算，不吃 LLM）
   0.50·词覆盖 + 0.22·标题命中 + 0.16·路径对齐 + 0.12·新颖度
   × status × confidence × kind_bonus
```

**为什么词法是主力**："上次关于 X 说了啥"里 X 是关键词，不是路径。实测 `解包 unity 资源` 不走路径过滤，覆盖率 100% 直接命中。

**为什么树不做召回**：树的价值是范围限定（`--path`）和浏览（这枝多少卡、多久没动）。让它做召回，等于逼用户把问题翻译成分类。

**为什么图不做通用召回**：`contains` 只补 2-3 条；杀手用途是 `supersedes` —— 回答"这个结论还有效吗"。

**为什么不吃 LLM 精排**：query 时刻不该等一次模型调用。实测纯计算排序在 680 卡规模上已经够准。

## 七、演化：不删，只降权

| 事件 | 动作 |
|---|---|
| 结论被推翻 | 旧卡 `superseded`，新卡 + `supersedes` 边 |
| 细节有补充 | 同标题正文更长 → 更新，保留原 id |
| 判断不确定 | `confidence` 调低，仍可命中但排后 |
| 确认过时 | 不删。删了就不知道"当初为什么放弃" |

检索时 `superseded` × 0.15，需 `includeSuperseded` 才可见。时间衰减半衰期 240 天。

## 八、判定标准

**一条卡**：下次会话的我在没有上下文的情况下读到它，能不能直接照做？不能就重写。

**一个库**：

- 问"是什么" —— 能答（卡）
- 问"为什么" —— 能答（decision 卡 + 图）
- 问"什么时候放弃的、换成什么了" —— 能答（superseded + supersedes）
- 问"继续上次" —— 能找回原话（L3 回指）

只有前两条能答的是检索系统，后两条也能答的才是记忆。

## 九、已知天花板

1. **分类靠关键词**。`topic/dsh` 会吃掉几百张卡，因为 "dsh" 出现频率高。这是纯规则归枝的极限，需要实体层才能细分。
2. **图只有 `contains`**。缺 entity 抽取（项目、文件、报错码、版本号）和 `uses / depends_on / contradicts`。"决策链为什么这么定"撑不起来。
3. **没有向量**。中英异构查询（"blender 材质" vs "material"）会排错，这是纯词法的天花板。
4. **ingest 需要外部触发**。还没接定时任务。

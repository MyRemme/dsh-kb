## R01 · P1 · 重扫覆盖人工修订并恢复失效卡

**触发**：吸收一份会话；用 `updateFact` 修正其正文并把状态设为 `superseded`；对未变化的会话执行 `ingest({rescan:true})`。

**实际**：正文从 `User corrected this answer.` 恢复成 `Original answer from session.`；状态由 `superseded` 变成 `active`；版本 2→3。过程没有报错。文件追加变化时也会走相同写入分支。

**原因**：`writeFact` 按固定来源找到旧卡后，无条件把经过 `payload` 补默认值的整份候选传给 `updateFact`。默认 `status='active'` 和源正文会覆盖人工字段。相比旧实现，这里新增了无条件同源覆盖与状态恢复；旧历史仍可查，但当前检索会重新使用已被用户否定的内容。

**建议**：记录最后吸收的来源基线，并区分来源字段与人工修订。来源未变时保持幂等；来源与人工同时变化时保留修订并报告冲突。至少不得由普通重扫恢复用户设置的失效状态。

**验收**：覆盖“吸收→正文/标签/状态人工修订→未变重扫”和“人工修订→来源追加→增量吸收”，确认修订和状态不会被静默覆盖。

## R02 · P1 · 可变来源去重导致错误归属

**触发**：同一项目的 s1、s2 两份 session 卡具有相同标题和正文；写入时二者去重为同一 id；随后只有 s1 的正文变化。

**实际**：s1 更新了共享卡。s2 原先返回的 id 现在也读到 `Only session one now says this`，但 `sources` 仍列着 s1、s2，没有版本绑定来表明 s2 仅支持旧正文。

**原因**：内容去重把独立可变来源合成同一个可变事实实体；`fact_source` 只关联 fact id。后续修订更新整个实体，并保留此前全部来源。保存历史正文不等于保存每个来源支持哪个版本。

**建议**：固定来源的原料使用独立身份；或为来源绑定内容版本/哈希，并在某一来源独立演进时分裂共享实体。不能让 s2 自动为仅出现在 s1 的新正文背书。

**验收**：同内容双来源→只更新其中一个→分别读取/追溯两个来源；来源支持范围应与其真实内容一致。补测更新第二个被去重来源的情况。

## R03 · P2 · 连续镜像编辑出现假冲突

**触发**：导出正文 v1；在文件改成 v2 并导入成功；直接在同一文件改成 v3，再导入。数据库没有其他写入。

**实际**：第一次 `updated=1`；第二次 `updated=0, stale=1`，报 `database-changed`，库内仍为 v2。

**原因**：第一次成功导入推进了数据库版本，但文件仍携带旧 `base`，也没有导入确认账本。下一次导入把自己上次成功的修改误当成并发冲突。

**建议**：导入成功后安全地确认新基线，可使用文件元数据或专用账本，并处理文件在确认期间被再次编辑的情况。不能要求用户用 `force` 才能正常连续编辑，也不能因此放松真实并发冲突检测。

**验收**：连续两次编辑导入均成功；在两次编辑之间加入独立数据库修改时仍准确拒绝覆盖。

## R04 · P2 · 同内容提炼没有产物却消耗原料

**触发**：原料是 `episode`，本身已包含简短结论。模型返回相同标题/正文、`kind='fact'`、合法来源引文，并把片段列入 `processed`。

**实际**：返回 `cards=1, added=0, updated=0, dup=1`，id 指向原料；库内仍只有 `episode`；边数 0；后续待提炼原料数 0。

**原因**：写入只按内容+scope 去重，忽略原料和结论的角色；结果 id 与原料相同，自环边被忽略，进度却照常提交。原料继续使用 episode 的排序/遗忘规则，预期的长期结论卡没有生成。

**建议**：明确原料和结论的身份边界，或者定义可验证的原料提升流程。只有目标结论确实落在正确的身份/类型上，才能将该处理结果视为成功。

**验收**：模型原样保留已足够简洁的结论时，仍能得到可检索的事实卡及可追溯来源。该问题与 R02 相关，但仅防止多 session 共用卡并不能修复此分支。

## R05 · P2 · 证据只存不读，来源追溯不完整

**触发**：提炼一条带证据的结论，再把来源从“需要 Node 22”修订为“需要 Node 24”，读取结论详情。

**实际**：`edge.note` 中确实存有源 `version=1`、hash、Node 22 引文；正式 `/fact` 返回的边却只有 rel/w/id/title/kind/path/ts，没有这些证据字段。来源详情指向当前 v2。

**原因**：`getFact` 两条关系查询都遗漏 `e.note`，`/fact` 与 `kb_get` 因而无法提供结论当时使用的证据。历史正文仍保存在历史接口中，但调用方没有证据关联来判断应核对哪个版本、哪段原文。

**建议**：将来源版本、哈希和引文作为结构化关系数据返回，工具详情也应显示；对来源已修订的情况明确提供原证据版本的定位信息。

**验收**：提炼→来源修订→通过公开详情/工具核验，能确定结论引用的是 v1 及其准确原文，而不是默认为当前来源正文。

## R06 · P2 · 未编辑镜像破坏正文精确保留

**触发**：写入正文 `\n\n  line with indent\n`，导出后不修改文件，直接导入。

**实际**：报告 `updated=1`，版本 1→2，正文变成 `  line with indent`。

**原因**：新写入口保留正文开头空行，但 `parseFrontmatter` 仍无条件剥除全部开头换行，导入因此把原样投影误判为正文修订。问题重点是原文开头空行丢失；不把已有的行尾/换行显示规范化单独算作另一项缺陷。

**建议**：精确解析元数据分隔符与正文边界，保留正文固有空行；原样往返必须不写库、不产生版本。

**验收**：正文包含 0/1/多行开头空行、缩进、CRLF 和尾部空白时，未编辑的镜像导入保持数据库正文与版本不变。

## R07 · P2 · 镜像 path 修改被忽略并误报成功

**触发**：导出的文件同时有 `path: "topic/one"` 和 `paths: ["topic/one"]`。只把 `path` 改为 `topic/two` 后导入。

**实际**：报告 `updated=1` 且无失败，库内 path 仍为 `topic/one`、version 仍为 1。

**原因**：解析时 `paths` 优先；一致性比较又使用了独立 `path`，因而判断有变化。真正更新只传旧 paths，并丢弃 `pathValue`；导入统计还忽略 `updateFact` 的 `unchanged` 结果。

**建议**：明确主路径与多路径字段的导入规则。修改主路径时同步更新主归属，冲突则明确报错；统计按真实写入结果计算。

**验收**：只改 path、只改 paths、两字段相互冲突分别产生明确且与库一致的结果。

## R08 · P2 · 失败重试绕过吸收文件上限

**触发**：准备 4 个截断会话文件，连续两次调用 `ingest({limit:1})`。

**实际**：每次都得到 `err=4, files=0`，四个文件都被解析并写入错误日志，完全没有被限制为一次尝试。

**原因**：上限检查使用 `stats.files`，该数只在解析/事务成功后增加；异常分支直接 continue。旧逻辑已有计数遗漏，本次允许失败文件持续重试后，错误文件会在每次运行重新触发无界批次。

**建议**：使用独立的处理尝试计数控制批次；保留成功/失败统计；未变化的成功缓存跳过可以不占额度。这里未实测宿主卡顿或崩溃，已证明的是批次上限失效。

**验收**：全失败、成功失败混合、重复失败批次均不超过指定尝试上限，且后续运行仍可继续处理剩余文件。

## R09 · P2 · 自动吸收留下过期摘要

**触发**：某枝只有一张 365 天前的 episode，调用正式 `POST /ingest`，会话目录为空。

**实际**：接口降级 1 张卡，树节点 `count=0`，但 `summary` 仍含 `1 张卡` 和该卡标题 `Old episode`。

**原因**：路由先 `digest`，后 `reap`。`kb_ingest` 的 `index.js:443–444` 及定时流程的 `index.js:730–732` 也先摘要再 sweep。直接调用 digest 清空空枝的单元测试通过，并不能覆盖真实工作流。

**建议**：完成吸收、降级和提炼写入后再刷新受影响节点摘要，避免后续状态变动立即使摘要失效。

**验收**：从正式 HTTP、工具和定时流程触发最后一张活跃卡降级，返回/显示的节点数量与摘要同步更新。

## R10 · P2 · 模型提炼成功被提示为没有通道

**触发**：正式 `/distill` 路由使用假模型成功生成并保存一张卡。

**实际**：API 返回 `cards=1, added=1, provider='fake', model='fake'`。前端判断 `result.distilled === undefined`，因此走“宿主没有可用的模型通道”的分支。

**原因**：生产实现返回 `cards`，前端成功分支读取 `distilled`。该不一致在修复前快照中就存在，此次未修复；不是模型不可用的实测结论。

**建议**：统一响应契约，并显式区分模型已执行、仅出料、无原料三种状态，不能用一个未约定字段缺失来推断没有通道。

**验收**：真实 `distillWithModel` 返回形状分别覆盖成功、空原料和无通道分支；面板消息应与实际结果一致。
